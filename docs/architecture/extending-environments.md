# 扩展环境与故障

环境来自 `simulator/environments/commerce.json`：服务节点包含 name、label、kind、公开 config、metric_keys，依赖是 from/to 边。新增节点和依赖后，MCP发现、前端布局、节点详情和状态传播无需修改组件。节点名必须唯一，依赖端点必须存在；载入时验证。不支持执行配置中的代码。

默认十节点：流量网关、订单API、支付、库存、异步Worker、通知消费者、Redis缓存、数据库连接池、数据库、消息队列，共十二条依赖。节点tier定义展示层；箭头是调用者→所依赖的服务，消费关系的箭头不是消息流向。默认六种因果故障：

| 故障 | 责任服务 | 观测指标 | 安全修复 |
| --- | --- | --- | --- |
| 共享连接池耗尽 | db_proxy | 连接占用/获取等待升高，但数据库查询和API CPU正常 | 重启共享连接池进程 |
| 连接泄漏 | worker | Redis连接数及API延迟/错误 | 重启责任Worker |
| CPU饱和 | api | CPU占用及API延迟/错误 | 重启API进程 |
| 慢查询积压 | database | 数据库延迟及API延迟/错误 | 重启模拟数据库进程 |
| 消费阻塞 | worker | 队列深度及API延迟/错误 | 重启消费者 |
| 队列进程退出 | queue | 服务停止、队列深度及API错误 | 恢复队列进程 |

这是模拟环境：重启会重置对应故障状态，指标按状态逐tick恢复，并传播依赖影响。SOP只用于当前实验；生产数据库故障不应照搬重启策略。

## 增加已有故障机制的场景

1. 在 `simulator/scenarios/` 添加JSON，提供唯一id、name、description、target、metric、fault.type/intensity、ground_truth、allowed/forbidden_actions及success。
2. 使用已实现的六种fault.type之一，确保目标、指标和故障机制匹配。强类型验证会拒绝未知故障类型和矛盾动作许可。
3. 重启控制服务后，场景选择自动出现；Agent只得到真实观测和告警，场景真值与评分不进入MCP。
4. 运行 `pytest tests/test_multi_scenario.py` 验证退化、错误修复无效、正确修复及持续恢复。

新增完全不同的故障机制需要显式扩展 `packages/contracts.py` 的故障类型、`simulator/world.py` 的因果状态变化和相应指标，添加通用诊断Skill/SOP与回归测试。系统不会把任意JSON标签当作已有可模拟能力。

## 排行与比较

榜单从SQLite中已完成的独立评估实时计算，无预置虚构分数。按场景等权计算恢复率、根因准确率、安全率，再以50/30/20加权并乘场景覆盖率；未测场景不计分，反复刷同一种场景不会替代覆盖。相同分数并列，未参评无名次。取消实验排除，失败/超时计入；恢复耗时仅统计成功任务。

可按场景筛选比较，始终同时展示样本数、覆盖率和Agent类型。当前是本机实验成绩，不代表跨环境或生产能力，也没有对不同版本Agent进行身份认证。

## 拓扑正确性与故障标记

服务健康从公开局部指标与运行状态推导，再沿依赖的反方向传播到调用者。健康依赖不会因其调用者异常而被染成异常；无关通知消费者停止不会让API直接失败。连接池故障会影响支付、库存、后台任务及API，但不把健康数据库伪装成故障点。

场景注入目标只写入控制平面的fault.injected事件用于操作员标记，MCP环境观测没有这个字段。图上的注入点是实验配置，Agent根因是独立产物，二者不可混同。历史回放仅使用当前游标可见事件；旧事件没有target时兼容公开场景目录。
